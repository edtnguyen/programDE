1. Purpose and scope
This document explains how to describe the analysis of CC-Perturb-seq data for an IGVF DACC submission. It covers the current analysis, which uses CC-Perturb-seq for FASTQ preprocessing, matrix generation, and differential gene expression analysis, and PerturbNMF for cNMF gene program analysis. It also explains how to organize files so the submission can line up with the IGVF CRISPR_Pipeline later.
The goal is to make the submission clear, reviewable, and easy to update after a future rerun with the IGVF CRISPR_Pipeline. The plan keeps a clear record of which software made each file.
The current plan covers four main parts: FASTQ preprocessing and matrix generation; differential or cis/trans analysis; PerturbNMF gene program analysis; and final summary tables, plots, and reports.
2. Main recommendation
This keeps the current submission close to what we already have while still making it easy to move to the IGVF CRISPR_Pipeline structure later.
3. DACC terms used in this plan
Some DACC object names are technical and should stay in the document because they are portal terms. The table below gives a simple meaning for each term.
4. Overall workflow
The workflow should be described as one overall analysis with four main steps. Step 2 and Step 3 both start from the processed cell x gene/guide matrix. Step 4 summarizes the PerturbNMF results.
5. Current run and future run
The current analysis and the future IGVF CRISPR_Pipeline rerun should be connected, but they should not be mixed together. The table below shows how to describe each step now and how to update it later.
6. Input files to prepare
The main change from the earlier draft is to make a standard set of input files that resembles the IGVF CRISPR_Pipeline input structure. These files can be generated from the current CC-Perturb-seq metadata and kept with the current submission.
This does not mean the current data were run with CRISPR_Pipeline. It only means the current metadata are organized in a way that will make a future rerun easier to compare.

7. Step-by-step analysis plan
7.1 Step 1 - Process FASTQs, assign guides, and create the main matrix
Minimum QC for Step 1: total reads per library, mapped reads/percentage, UMI saturation, cell calling method and threshold, number of called cells, genes/UMIs per cell, mitochondrial percentage, guide UMI distribution, cells with one/multiple/no guide, guide diversity, batch/plate/well representation, barcode recovery behavior, and final matrix dimensions.
7.2 Step 2 - Make differential results and cis/trans tables when supported
Minimum QC for Step 2: model formula, covariates, normalization method, guide filtering threshold, cells per guide/target, control guide set, guide-to-target grouping rule, cis distance or predefined-pair rule if used, multiple testing correction, effect size units, p-value/q-value definitions, and a column dictionary for each TSV.
7.3 Step 3 - Run PerturbNMF gene program analysis
Minimum QC for Step 3: input matrix layer and dimensions, filters before cNMF, K grid, selected K, threshold, random seeds, CPU/GPU path, reconstruction error, explained variance, stability, program count, enrichment results, perturbation sensitivity method, calibration method, and non-targeting guide behavior.
7.4 Step 4 - Prepare final summaries and reports
Minimum QC for Step 4: final selected K, retained and excluded program counts, exclusion reasons, program label rules, annotation evidence, external data sources, manual review status of any LLM-generated annotations, and final list of tables/figures to release.
8. Output files to submit or keep for review
This section lists the current files, the future CRISPR_Pipeline-style files, and the likely DACC object or content_type. The current submission should include files that actually exist, plus only conversions that were generated with documented code.
8.1 Minimal current-run submission package
Native CC-Perturb-seq MatrixFile: annotated cell x gene/guide h5ad, or matrix tar/MTX plus cell/gene/guide annotations.
Generated metadata files: original_samplesheet.tsv, guide_metadata.tsv, barcode/sample/well maps, reference_manifest.tsv, run_parameters.tsv, software_versions.yml or TSV.
Current differential output tables, using generic DACC content_type labels unless the current outputs are truly cis/trans.
PerturbNMF program outputs: cNMF h5mu if accepted, plus flattened gene program and regulator TSVs.
QC tables and column dictionaries for every submitted TSV/CSV.
8.2 Future CRISPR_Pipeline rerun package
Use the same samplesheet and resource files, updated with the exact CRISPR_Pipeline run settings.
Submit CRISPR_Pipeline outputs: inference_mudata.h5mu, cis_per_guide_output.tsv.gz, cis_per_element_output.tsv.gz, trans_per_guide_output.tsv.gz, trans_per_element_output.tsv.gz, and catalog_per_element_output.tsv.gz if DACC accepts it.
Create new AnalysisStepVersion records for Step 1 and Step 2 rather than changing the current CC-Perturb-seq records.
Run or relink PerturbNMF Step 3 using the CRISPR_Pipeline h5mu/RNA modality as input. Reuse current PerturbNMF links only if the actual input matrix is unchanged.
9. Software and version records
DACC will need Software and SoftwareVersion records for each main tool used in an AnalysisStepVersion. Use exact tags when possible. If a tag is not available, ask DACC whether an exact commit SHA and archive URL are acceptable.
10. QC and documentation
Each submitted table should have enough information for DACC and later users to understand how it was made. At minimum, include run parameters, software versions, QC metrics, and a column dictionary.
10.1 Column dictionary
Create a column dictionary for each submitted TSV/CSV, or one combined dictionary if easier. This helps DACC review the files and makes the tables easier to reuse.
11. DACC submission checklist
Create the combined workflow GitHub repository and tag it, for example v0.1.0-dacc-draft or v1.0.0 when finalized.
Tag the exact CC-Perturb-seq and PerturbNMF code versions used, or document exact commit SHAs and archive URLs accepted by DACC.
Check whether Software and SoftwareVersion records already exist in the portal; create missing ones with DACC.
Finalize the four AnalysisStep records, including step_label, title, parent step, analysis_step_types, input_content_types, and output_content_types.
Create AnalysisStepVersion records and link each one to the correct SoftwareVersion records.
Generate the standard input files: original_samplesheet.tsv, seqspec files, guide_metadata.tsv, barcode files, reference_manifest.tsv, run_parameters file, and software_versions file.
Generate a file manifest with submitted_file_name, md5sum, file_format, content_type, reference_files, derived_from, file_set or analysis_set, controlled_access, and analysis_step_version for each submitted output.
Create column dictionaries for every TSV/CSV output.
Run DACC validation/checkfiles on TSV/CSV outputs where applicable and revise files as needed.
Prepare a short README for reviewers that explains the current CC-Perturb-seq run and the future CRISPR_Pipeline rerun plan.
12. Questions for DACC
1. Should Step 4 reporting be a separate AnalysisStep, or should it be merged into Step 3 because it mostly summarizes PerturbNMF outputs?
3. For the current matrix, should native h5ad remain primary, or should we also provide a converted h5mu?
4. Which content_type should be used for catalog_per_element_output.tsv.gz?
5. For current differential outputs, should we use generic differential content types unless the outputs are explicitly cis/trans?
6. Should HTML/PDF/Excel reports and plots be submitted to the portal, or kept as QC/supporting review files?
7. Which software dependencies should be separate SoftwareVersion records versus recorded only in the environment or software_versions file?
8. Which Software objects already exist in the portal, and which custom records need DACC creation before file submission?
